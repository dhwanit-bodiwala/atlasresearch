The module is organized around a thin FastAPI application layer (`main.py`) that mounts two routers — `/chat` (conversational follow-up) and `/ingest` (PDF/MD/TXT upload) — plus a synchronous `/research` endpoint and an asynchronous `/ws/research` WebSocket stream. The WebSocket path runs the blocking `run_orchestrator` on a worker thread via `asyncio.to_thread`, bridging it to the event loop through a `queue.Queue` and emitting structured JSON events via `ws_events.emit_event`. The core orchestration logic lives in `orchestrator.py`, which sequentially invokes three agents: `gatherer` (web search + fact extraction), `synthesizer` (write coherent answer from findings + notes), and `critic` (flag unsupported claims). Each agent is implemented as a standalone module (`gatherer.py`, `synthesizer.py`, `critic.py`) with a `run_<agent>` function accepting `(question, project_tag, emit=None)`, making them independently testable. Model interaction is abstracted through `ollama_services.call_agent`, which resolves the role-specific model, system prompt, and token limit from `agent_config.py` (tiered by `CURRENT_TIER`: cpu-low, cpu-high, gpu). Persistent state is centralized in `read_write_action.py`, which uses `psycopg2` + `pgvector` for semantic search over a `memories` table keyed by `project_tag` and `type` (RAW_FINDING, SYNTHESIS, FLAGGED, NOTE, CORRECTION). Dependency direction is strictly one-way: HTTP layer → orchestrator → agents → ollama_services / read_write_action; agents never import each other.
